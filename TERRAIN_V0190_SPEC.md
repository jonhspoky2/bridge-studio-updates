# Bridge Studio v0.19.0 — Terrain Sculpting: техническое задание и критерии выпуска

**Статус:** разработка, только ветка `feature/terrain-editor-v0190`. Не переключать подписанный канал обновлений до прохождения всех ворот. **База:** опубликованная v0.18.5.

## 1. Объём именно этого этапа

Пользователь создаёт/открывает рельеф, выбирает **Terrain**, видит область кисти на поверхности, одним непрерывным мазком формирует ландшафт с четырьмя кистями (**Raise / Lower / Smooth / Flatten**) и настройками **Radius / Strength / Hardness**. Один мазок отменяется одним Undo/Redo. Общие границы участков остаются без швов. Изменения сохраняются в `.rwscene`, работают в Play и экспортированном WARPGAME HTML.

Релиз должен обеспечить *полный вертикальный сценарий* «создать → нарисовать → отменить → сохранить → переоткрыть → пройти по склону → экспортировать», а не просто панель кнопок.

**Не входит:** покраска четырьмя материалами (v0.19.1), генерация пещер/вокселей, сложная эрозия, бесконечный мир, Terrain LOD и изменение архитектуры C# хоста. Качественный вид UI и живой предпросмотр кисти входят в текущий этап, однако техническая тестовая сетка не выдаётся за готовый художественный мир.

## 2. Основание и существующие ограничения

- `src/terrain_core.js`: heightfield v1, `chunks[{x,z,step,segments,heights}]`, максимум 64 чанка / 100000 вершин, единое разрешение, швы валидируются.
- Координаты узлов: `x + col*step`, `z + row*step`. Сетка рисуется двумя треугольниками на квадрат, высота `sampleHeight` считается по той же диагонали.
- `src/studio.js`: старый Undo хранит полный JSON; `refreshTerrain` создаёт весь Terrain с нуля; `initRenderer` связывает события canvas и манипуляторы.
- `src/game_runtime.js`: читаемая версия `doc.terrain`, общий код рендеринга и высоты. Физика не должна зависеть от редакторских кистей.
- `tools/build_studio.py`: собирает монолитный HTML из `src`. Расширения должны попасть в модульные исходники и одинаково включаться в редактор и Play/Build.
- `WARPGAME`: жёсткое ограничение **3000000 байт** *собранной игры*, НЕ редактора.

## 4. Модель кисти

- Точка попадания — `Raycaster.intersectObjects(terrainMeshes)` (в мировых координатах). У `terrainMeshes` индексы соответствуют `terrain.chunks`.
- Радиус в единицах мира, рабочий диапазон 0.5–16. Strength — скорость изменения высоты (единицы мира за секунду) с диапазоном 0.1–12; Hardness 0–1 — доля внутренней области полного воздействия. Falloff за пределами Hardness по `smoothstep`.
- Raise: `h += strength * dt * weight`; Lower: `h -= strength * dt * weight`.
- Flatten: высота-цель фиксируется в момент начала stroke по `sampleHeight`, затем `h += (target-h) * clamp(strength*dt*weight,0,1)`.
- Smooth: усреднить соседа 3×3 с учётом доступных узлов, вычислять все целевые значения **до** записи одного даба (нет зависимости от порядка обхода), интерполировать с тем же коэффициентом.
- Выход за границу Terrain не создаёт новые вершины. При переполнении [-1000,1000] ограничивать значения. При отсутствии попадания последний drag не должен перемещать камеру/объект.
- Stroke должен равномерно покрывать путь между двумя pointer-событиями (шаг не больше половины шага сетки либо радиуса/3, в разумных пределах). На долгих паузах обрабатывать удержание без бесконечной интенсивности; исключить зависимость эффекта от частоты событий.
- Пустой stroke не изменяет проект и не создаёт историю.

## 5. Архитектура Undo

Команда `{kind:'terrain-stroke', changes:[{chunk,index,before,after}], ...}` хранится в общем `undoStack`. Команды другого типа сохраняют текущую сериализованную форму.

`historyBack` и `historyForward` обязаны корректно переключаться между обычными JSON-снимками и terrain delta-командами. Дeltas не перезаписывают `project`; они меняют только `terrain.chunks[chunk].heights[index]`, затем обновляют нужные чанки.

Важно: когда начинается stroke, все затрагиваемые высоты до первого изменения запоминаются один раз. При commit команда записывается только если есть изменения. Cancel возвращает значения до stroke и не загрязняет историю.

## 6. Обновление геометрии и нормалей

- В редакторе хранить соответствие `chunkIndex → mesh`. Перезаписывать позиционные Y компонентов только в dirty chunks.
- Нормали пересчитывать в изменённых чанках и в непосредственных соседях по сетке (при изменениях близко к общей границе). Учитывать совместимость Triangle sampling.
- `BufferGeometry.computeBoundingSphere`/boundingBox и атрибуты обновлять перед следующим render, чтобы Raycaster не пропускал новый холм.
- Подход к удалению Terrain: dispose geometry/material ровно один раз; не забывать о WebGL-ресурсах при открытии другого проекта.

## 7. Работа в редакторе

Формат панели:

**Terrain**
Создать плоский рельеф (2×2, 16×16, шаг 1 по умолчанию). При уже существующем Terrain — не перезаписывать данные молча.

**Инструменты**
Raise | Lower | Smooth | Flatten
Radius (0.5–16) | Strength (0.1–12) | Hardness (0–1).

В режиме Terrain наводишь курсор и видишь кольцо кисти, нажимаешь и ведёшь — рельеф изменяется в реальном времени. Средняя/правая кнопка мыши оставляет управление камерой. Escape во время stroke откатывает именно текущий мазок. В режиме Play кисти не активны.

## 8. Тестовая матрица

**Core/unit:** все 4 кисти; границы чанков по X/Z, углы 4 чанков; разная жёсткость и радиус; быстрый drag; clamp [-1000,1000]; smooth не зависит от порядка; отсутствие мутаций при пустом stroke; проверки плохих входных данных; совместимость flat/demo старого Terrain.

**Browser/UX:** положительные/отрицательные дельты; pointerup/pointercancel/Escape; Undo/Redo; переключение Move/Terrain/Play; hover; реальные кадры рельефа; отсутствие ошибок консоли; Play/Stop не мутирует проект; сохранённая и повторно загруженная сцена совпадает; экспортированный HTML в лимите WARPGAME.

**Regression:** `tests/terrain-core.cjs`, `tests/terrain-browser.cjs`, `tests/play-v0184.cjs`, `tests/patch-save-v0182.cjs`, контроль импортированного GLB, игры без Terrain.

**Measurement:** карты 2×2×16 и 4×4×32. Собирать P50/P95 времени даба, число обновлённых чанков, время кадра, число треугольников, память браузера по возможности и размер экспортируемого HTML. Целевые пороги утверждать по измерениям, не объявлять произвольные FPS доказанными.

## 9. Порядок исполнения и контрольные ворота

1. A+B+C: unit-тесты; нельзя переходить к UI при несовпадении общих границ.
2. D+E: интеграция истории и инкрементального WebGL; нельзя переходить к релизу при полной пересборке сцены на каждый dab.
3. F: визуальная панель и управляемый brush preview с ручной проверкой изображения.
4. G+H: полные browser/Play/Export/QA-прогоны; исправить флейки до релиза.
5. Подписанная сборка: `python tools/build_studio.py --check updates/v0.19.0/studio.html`, sha256, подпись штатным ключом, CI, GitHub Pages. Сначала payload в `main`, потом переключить подписанный манифест.
6. Windows Smoke Test после установки: сохранить реальный .rwscene, открыть, перейти в Terrain, нарисовать холм, Undo/Redo, Play, Stop, экспорт. Статус Windows не подтверждать автоматически.

**Определение завершённости v0.19.0:** пользователь создаёт карту не из заранее зашитого склона, а рисует рельеф мышью четырьмя кистями и получает идентичную коллизию/картинку в редакторе, Play и WARPGAME. Без этого `v0.19.0` не публиковать.
